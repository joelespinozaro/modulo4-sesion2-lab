Del agente que funciona

En la Sesión 1 el asistente del instituto aprendió a razonar, actuar y colaborar. Hoy sale a producción por WhatsApp, con cientos de alumnos reales. Esta guía recorre lo que necesita alrededor: skills para cargar contexto solo cuando hace falta, hooks y guardrails para controlar lo que entra y lo que sale, una fallback chain para no dejar a nadie sin respuesta, pruebas para saber si algo empeoró y los patrones que ordenan todo. 01

En la demo funcionaba. Con alumnos reales aparecieron cinco problemas

Panorama · Producción

El agente ya responde preguntas, consulta documentos y usa tools. Funcionaba perfecto en el notebook. Pero cuando lo conectas a WhatsApp, los alumnos escriben su DNI, alguien intenta engañarlo, el proveedor del modelo se cae en hora punta y el prompt ya tiene dos mil líneas. Ninguno de esos problemas se arregla con un mejor modelo. Se arreglan con ingeniería alrededor.

Idea 1

El contexto se carga bajo demanda

Un manual gigante enviado en cada mensaje cuesta tokens y distrae al modelo. Las skills se abren solo cuando la pregunta las necesita.

Idea 2

Todo pasa por puntos de control

Antes y después del modelo hay hooks que revisan, limpian, bloquean o reintentan. El agente no sabe que existen.

Idea 3

Lo que no se prueba, se rompe

Un cambio de una palabra en el prompt puede romper diez casos. Las pruebas y las evaluaciones te avisan antes que el alumno.

La sesión sigue ese orden: qué sabe el agente (skills), qué controla (hooks y guardrails), cómo resiste (fallback chain y prompts versionados), cómo se prueba (testing) y cómo se arma (patrones). Al final lo construyes en cuatro laboratorios encadenados, con el asistente respondiendo en tu celular.

Cómo leer este material

Cada bloque tiene una explicación corta y un artefacto con el que puedes experimentar. Nada se mueve solo: tú avanzas con los botones. Al final hay un glosario y un cuestionario de 5 preguntas.

02

El problema: un manual que el modelo lee entero en cada pregunta

Context engineering · Qué sabe

Primero aprendimos a escribir buenos prompts. Después empezamos a meter todas las reglas en un archivo grande, tipo AGENTS.md o CLAUDE.md, que viaja en cada llamada. Funciona hasta que el archivo tiene dos mil líneas y el alumno solo escribió «hola».

Prompt engineering es redactar bien una instrucción. Context engineering es decidir qué entra en toda la ventana de contexto en cada llamada: instrucciones, historial, resultados de tools, documentos y la pregunta. Cada token que entra cuesta dinero y compite por la atención del modelo. Una regla sobre ciberseguridad no ayuda a responder una pregunta sobre horarios: solo estorba.

Idea clave

No se trata de escribir menos reglas, sino de cargar cada regla solo cuando la pregunta la necesita. En AGENTS.md quedan las reglas que aplican siempre: idioma, tono y límites del negocio. Todo lo específico de un área se mueve a una skill.

03

Una skill es una carpeta, y solo un archivo es obligatorio

Anatomía · Qué sabe

Una skill es conocimiento empaquetado: instrucciones, y si hace falta, scripts y documentos de apoyo. Vive en una carpeta con un archivo SKILL.md. Lo demás es opcional.

El formato es un estándar abierto (Agent Skills, publicado por Anthropic en diciembre de 2025) que hoy leen Claude, Codex, Gemini CLI, GitHub Copilot, Cursor y decenas de herramientas más. Por eso una skill bien escrita se reutiliza entre agentes y proveedores sin reescribirla.

Regla práctica

La description decide si la skill se usa. Escríbela como el asunto de un correo: qué hace y cuándo usarla. Si el modelo no la entiende, la skill no existe.

04

De un texto a un flujo completo: cuatro tipos de skills

Tipos de skills · Qué sabe

No todas las skills son iguales. Algunas son solo un procedimiento escrito. Otras traen código que el agente ejecuta. Crecen según lo que necesitan para hacer su trabajo, y con ellas crecen los permisos que pides.

Ojo

Una skill no ejecuta nada por sí sola. El agente la lee y decide. Una skill con scripts necesita un entorno donde correr código, como el sandbox de la API del proveedor o tu propio servidor.

05

Skill, tool, RAG y subagente no compiten: se combinan

Relaciones · Qué sabe

Es fácil confundirlos porque los cuatro llegan al modelo por caminos parecidos. La diferencia está en qué aportan y en quién hace el trabajo.

Una skill le enseña al agente cómo hacer algo: entra al contexto del mismo agente, no tiene su propio modelo ni su propio loop. Una tool es una acción que el agente ejecuta. Un RAG casi siempre se expone como una tool más (retrieve_documents). Un subagente es otro agente completo, con su propio contexto y sus propias tools, que recibe una tarea y devuelve solo el resultado. Por eso una skill puede decir «primero busca con retrieve_documents y luego llama a generate_pptx».

Si te preguntas…UsaEjemplo en el institutoCosto de contexto
¿Necesito un procedimiento o criterio que no siempre aplica?SkillCómo armar una ruta de aprendizajeUnos 100 tokens hasta que se carga
¿Necesito ejecutar una acción o leer un dato vivo?ToolRegistrar una matrícula, ver el climaUna llamada por uso
¿Necesito responder con información del negocio?RAGPrecio y duración de un programaBúsqueda más los fragmentos
¿Es una tarea larga, con otras tools, que ensucia el contexto?SubagenteAnalizar todas las ventas del mesOtro loop completo
Regla de costo

Skill antes que subagente. Un subagente es otro agente completo con su propia cuenta de tokens. Si comparte todo el contexto con el principal y no tiene tools propias, probablemente debió ser una skill.

06

El agente sabe que la skill existe, la abre si la necesita

Progressive disclosure · Qué sabe

La carga es en tres niveles. El menú siempre está a la vista, el capítulo se abre cuando la pregunta calza y los anexos solo si la tarea lo pide. Así puedes tener cincuenta skills instaladas y el modelo solo carga un menú corto.

En el laboratorio

Lo verás funcionar en la Parte 2: SkillMiddleware pone el nivel 1 en el system prompt y la tool load_skill trae el nivel 2 cuando el modelo la pide.

07

Dónde se consumen las skills y cómo se publican

Canales y ciclo de vida · Qué sabe

La misma carpeta puede llegar al agente por distintos canales. Y como es código, vive en un repositorio con revisión, pruebas y despliegue, igual que el resto del sistema.

Canal 1

Apps de agentes

Claude, Codex, Gemini CLI, Copilot y Cursor leen la carpeta de skills sin escribir código.

Canal 2

API del proveedor

La API de Claude carga skills en un contenedor con ejecución de código. La de OpenAI las monta en su herramienta shell.

Canal 3

Tu framework

En LangChain o ADK escribes la carga tú: un middleware y una tool. Es lo que haremos en el lab.

Canal 4

Servidor compartido

Un servidor MCP o una API interna publica las skills para varios agentes. Así lo hace la rama parte-4-guardrails.

Rollback

Si una versión de la skill baja las métricas, se revierte el commit o se fija la versión anterior. Igual que con el código.

08

Un hook es un punto de control en el camino del agente

Hook patterns · Qué controla

Piensa en los controles de un aeropuerto. El pasajero no los diseña, pero pasa por todos: check-in, seguridad, embarque. Ninguno cambia el avión. Un hook hace lo mismo con cada mensaje: se engancha en un punto fijo y revisa, limpia, mide o bloquea, sin tocar la lógica del agente.

Antes del modelo

Pre-processing

Proteger datos personales, recortar textos enormes, controlar el presupuesto de tokens, bloquear intentos de manipulación.

Después del modelo

Post-processing

Revisar la respuesta, exigir un formato, adaptar el texto al canal y registrar métricas.

09

Dos estilos: el que observa y el que envuelve

Node-style y wrap-style · Qué controla

Un hook node-style es un control en un punto fijo: mira el estado y deja pasar, modifica o corta. Un hook wrap-style recibe la llamada completa como una función: tiene código antes, decide si la hace (y cuántas veces) y tiene código después.

Para el wrap, piensa en el asistente que acompaña al pasajero todo el viaje. Si el vuelo se cancela, lo reprograma (reintento). Si ya tiene la respuesta, ni lo sube al avión (caché). Si eres desarrollador, es como un decorador de Python o un try/except alrededor de la llamada.

Regla

Para mirar o bloquear, node-style. Para reintentar, cachear o cambiar la llamada antes de hacerla, wrap-style.

10

La middleware chain no es de LangChain: es un patrón de siempre

Middleware chain · Qué controla

Si trabajaste con Express, Django, ASP.NET o FastAPI, ya conoces la idea: cada pedido pasa por una cadena de funciones antes y después del handler. Los frameworks de agentes aplicaron lo mismo alrededor del modelo y de las tools, cada uno con su nombre.

FrameworkCómo lo llamaDónde intercepta
LangChain v1AgentMiddlewareAntes, después y alrededor del modelo y de las tools
Google ADKcallbacks y pluginsAntes y después del agente, del modelo y de cada tool
OpenAI Agents SDKguardrails y hooksGuardrails de entrada, de salida y de tools
Claude Agent SDKhooksPreToolUse, PostToolUse, Stop y otros eventos
Microsoft Agent FrameworkmiddlewareSobre el agente y sobre cada función
CrewAIhooks, guardrails y callbacksPor paso y por tarea

En la cadena el orden importa. Los hooks de entrada corren de arriba hacia abajo, los de salida de vuelta, y los wrap se anidan como capas de una cebolla. Este es el orden real de la rama parte-3-hooks.

Corte temprano

Si TokenBudget corta en la ida, el modelo nunca se llama: ahorras costo y latencia. Cambiar el orden de la lista cambia el comportamiento del agente.

11

Protección de datos personales: bloquear, enmascarar u ocultar en logs

PII · Qué controla

Lo que envías al proveedor del modelo queda en sistemas de terceros, y en el Perú aplica la Ley 29733 de Protección de Datos Personales. Los datos que identifican a una persona (nombre, DNI, correo, celular) se llaman PII, por Personally Identifiable Information.

La herramienta de referencia es Microsoft Presidio: un Analyzer que detecta los datos y un Anonymizer que los reemplaza. Presidio no trae el DNI peruano, por eso la capa de datos personales del lab agrega DNI y RUC con expresiones regulares. No hay una sola estrategia correcta: el laboratorio usó las tres.

Decisión real

En la rama parte-5-produccion se desactivó el bloqueo porque rompía la matrícula, que necesita el DNI. La protección pasó a un filtro que oculta el dato en los logs. La estrategia depende del flujo que proteges.

12

Guardrails en capas: un menú, no una receta

Defensa en profundidad · Qué controla

Un guardrail es un filtro de seguridad. En vez de confiar en uno solo, se apilan varios en orden fijo, de lo más barato a lo más inteligente, y el primero que detecta un problema corta la ejecución. Estas son las ocho capas del laboratorio. No son obligatorias: elige según el riesgo de tu caso.

Regla 1

Short-circuit

La primera capa que bloquea corta el resto. No se gasta en las capas caras.

Regla 2

Fail-close

Si el clasificador no responde a tiempo, se bloquea. Nunca se deja pasar por error.

Regla 3

Reglas en YAML

Los patrones se editan en archivos de configuración, sin tocar el código.

Regla 4

Auditoría con hash

Se registra el SHA-256 del mensaje, nunca el texto que podría tener datos sensibles.

Cómo elegir

Un FAQ público quizá necesita las capas 1, 2 y 3. Un banco necesita las ocho. Suma capas según el daño que puede causar el agente.

Dato actualizado

La capa 8 usaba Llama Guard 4, pero Groq lo retiró el 5 de marzo de 2026. El repo ahora usa openai/gpt-oss-safeguard-20b: un modelo al que le pasas tu propia política (las categorías S1 a S13) y responde un JSON con violation 0 o 1. Si la respuesta no se puede leer, la capa bloquea. Es una buena lección de producción: los modelos que usas también se retiran.

Diseño del lab

La rama parte-5-produccion combina las dos cosas: Model Armor revisa entrada y salida, las capas 1 (secretos) y 4 (reglas del negocio) siguen siendo propias, y si Model Armor falla cae al pipeline local. Lo genérico se compra, lo propio del negocio se construye, y lo comprado siempre necesita un plan B.

14

Fallback chain: nunca dejar al alumno sin respuesta

Resiliencia · Cómo resiste

El reintento y el circuit breaker ya los conoces: protegen una llamada. La fallback chain protege la respuesta completa. Es una lista ordenada de alternativas: se prueba la primera, y si falla se baja un escalón. El último escalón siempre responde algo útil.

A esto se le llama graceful degradation: responder peor, pero responder. Un mensaje honesto («estamos con demoras, te escribo en unos minutos») es mejor que un error 500. Y mide en qué escalón respondió cada pedido: si muchos caen a la caché, la alerta debe sonar.

En el lab

El Gateway ya hace el último escalón: si el Agent API falla, envía un mensaje amable. En parte-5-produccion la idea se aplica a seguridad: si Model Armor falla, los guardrails caen al pipeline local.

15

El prompt es código: se versiona, se revisa y se prueba

Prompts a escala · Cómo resiste

Cambiar «responde en español» por «responde en español neutro» parece inocente. Pero puede cambiar cómo responde el agente en cientos de conversaciones. Por eso el prompt merece lo mismo que el código: versión, revisión y pruebas antes de publicar.

Promptfoo

Un A/B test de prompts

Herramienta open source de línea de comandos. Corres dos versiones del prompt contra los mismos casos y comparas. Úsala antes de cambiar un prompt que ya está en producción.

DSPy

El prompt lo escribe un optimizador

Declarative Self-improving Python. Defines qué entra, qué sale y cómo medir el éxito, y un optimizador busca el mejor prompt con tus ejemplos. Llega después, cuando ya tienes un dataset.

Regla

Ningún prompt llega a producción sin pull request y sin correr la evaluación. Para empezar basta con versionarlo en git y probar cada cambio con Promptfoo.

16

La pirámide de pruebas, con dos pisos que antes no existían

Testing de sistemas de IA · Cómo se prueba

Abajo van muchas pruebas baratas y rápidas. Arriba, pocas pruebas caras que miran el comportamiento real. La IA agrega dos pisos: el snapshot del prompt y las evaluaciones, porque un cambio de texto puede romper el agente sin romper una sola línea de código.

La evaluación continua cierra el ciclo. En la rama parte-5-produccion el alumno marca una respuesta como correcta o con error (/api/feedback). Los casos fallidos se suman al dataset. Luego /api/evaluate puntúa con RAGAS (Retrieval-Augmented Generation Assessment) y con un LLM-as-a-judge, un modelo que califica con una rúbrica. Si el puntaje baja, la versión no se publica.

Ojo con el juez

Un modelo evaluador también se equivoca. Sirve para revisar a escala, pero valida una muestra con el experto del negocio.

17

Cuatro patrones clásicos que ya usaste hoy sin nombrarlos

Design patterns · Cómo se arma

GoF viene de Gang of Four, la «pandilla de cuatro»: Gamma, Helm, Johnson y Vlissides, autores del libro Design Patterns de 1994. Le pusieron nombre a 23 soluciones que se repiten en el software, en tres familias: creacionales (cómo se crean los objetos), estructurales (cómo se combinan) y de comportamiento (cómo se reparten el trabajo).

Un agente es software. Los mismos problemas aparecen, y los mismos patrones los resuelven. Si nombras el patrón, tu equipo entiende el diseño en una frase.

Siete pasos entre WhatsApp y el agente

Arquitectura del lab · Laboratorio

El laboratorio conecta el asistente del instituto a WhatsApp. WAHA (WhatsApp HTTP API) expone tu número como una API REST. El Gateway traduce entre WAHA y el agente, y se comporta como una persona: marca leído, muestra «escribiendo…» y responde.

Detalle clave

El webhook responde «received» al instante y procesa en segundo plano. Si esperara al agente, WAHA creería que falló, reintentaría y el alumno recibiría respuestas duplicadas.
